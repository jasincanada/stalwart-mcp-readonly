App ideas for the Stalwart API

Written 2026-10-07, next to the API study. These are the programs worth building. Each one uses one door. None of them need both an API key and a mailbox password in the same process.

The official stalwart-cli already is the general admin client. It downloads /api/schema and can get, query, create, and update every management object. Do not rebuild that. Build the narrow tools below.

1. Read-only mailbox MCP

This is the repo's own job, and it is still the best first app. Door 1 only. An app password with read rights. Methods: Mailbox/query, Email/query, Email/get. Return headers, dates, mailbox names, and short snippets. Do not implement send. Do not write mail into git.

Why it fits: a person can ask "what arrived from this domain last week" without handing an agent the account password or the right to submit mail. The session call we already proved works is the whole login.

2. Header and authentication export

Door 1. A small command that, given a message id, writes a JSON file of the headers that matter in a dispute: From, To, Date, Message-ID, Received, Authentication-Results, and DKIM-Signature. It does not save the body.

Why it fits: the SMTP test on this server showed the signed copy and the JMAP draft are different objects. An export that records which copy you opened, and whether DKIM headers are present, is more useful than another mail client.

3. Outbound delivery doctor

Door 2. Read x:QueuedMessage/query and open GET /api/live/delivery/{domain}. Show one page: queued, retry time, and the live stages (DNS, TLS, SMTP reply). No button that deletes a queue item in version one.

Why it fits: when a message sits, the admin UI makes you hunt. A page that answers "is it DNS, TLS, or the remote server" is the daily tool. Live delivery is not an enterprise-only stream.

4. DKIM key watch

Door 2. Read x:Domain and x:DkimSignature. Compare the active selector with the TXT record in DNS. Warn when a key is marked active but is not published, or when a retiring key is the only one that resolves.

Why it fits: the 0.16.25 changelog includes a bug where a failed key rotation retires the old key and mail goes out unsigned. A watch that runs every morning catches that before a recipient does.

5. Credential expiry list

Door 2, read-only. x:ApiKey/query and x:AppPassword/query. Show description, created date, expiry, and allowed IPs. Never request or print the secret field. A later version can revoke by id. Creating an app password for another person is not available to an admin, so this app should not pretend it can.

Why it fits: secrets are shown once and then only a hash remains. The useful program is the inventory, not a second copy of the secret.

6. Listener and certificate checklist

Door 2. Read x:NetworkListener and x:Certificate. Print a table of bind address, port, TLS mode, and certificate expiry. Flag listeners whose address is not on this machine.

Why it fits: after the upgrade, two configured listener addresses failed to bind and the real ports still came up. A checklist makes that visible without reading the log file.

What not to build yet

  • A general settings editor. stalwart-cli and the admin UI already do this, and a homemade editor can break mail.
  • One program that holds an API key and a mailbox password. Split them into two apps so a mail-reading bug cannot change server settings.
  • A sender. Submission works, and local delivery can keep an unsigned draft while skipping the signed copy as a duplicate. A send button needs its own design, after the read path is boring and correct.
