A web page for app passwords

Written 2026-10-07, next to the API study. This server can already manage app passwords in a browser. A smaller page of our own is also possible. It uses Door 2, the management API, while the person is signed in as themselves.

The page Stalwart already ships

The Account Manager is part of the Stalwart web UI. On this server that UI is https://emailadmin.cryptocomputing.ca. After the mailbox owner signs in, the screen is Account › Credentials › App Passwords. The self-service path is also described as /account.

That screen can list passwords, create one, and revoke one. The person types a description, and may set an expiry and a list of allowed IP addresses. Stalwart invents the secret and shows it once. The person pastes it into the mail client. Closing the dialog hides it forever. Revoking one password does not change the account password or any other app password.

An administrator can open another user's list, look at it, and revoke an entry. An administrator cannot create an app password for someone else from that screen. The signed-in user creates their own. Stalwart staff have said an admin CLI session with impersonation can create one. The secret is still chosen by the server. You cannot type your own password.

This server stores accounts in its own RocksDB directory, not in LDAP or SQL. The built-in screen applies. No external directory has to hold the secret.

What a password is allowed to do

Each app password is an x:AppPassword object. The fields a page should show are:

FieldWho sets itMeaning
descriptionThe userA label such as "phone" or "read-only agent". Required.
secretThe serverShown once in the create response. Later reads do not return it.
createdAtThe serverWhen it was issued.
expiresAtThe user, optionalAfter this moment the password stops working.
allowedIpsThe user, optionalIP addresses or ranges that may use it. Empty means no IP limit.
permissionsThe userInherit copies the account. Replace allows only the named rights. Disable starts from the account and removes some rights.

For a mail-only or agent password, use Replace and name only the mail rights that client needs, such as IMAP or JMAP read. Inherit is shorter to build and gives the app password the same reach as the account password, including the web UI. That is the wrong default for a script.

The password is then used as a normal password on IMAP port 1143, SMTP port 1587, and https://webmail.cryptocomputing.ca/jmap/. It is not an API key. It does not call POST /api.

How our own page would talk to the server

The page signs in as the mailbox owner, with the account password, against https://emailadmin.cryptocomputing.ca. It then posts to /api with urn:stalwart:jmap. Three calls cover the screen.

List:

x:AppPassword/query
then x:AppPassword/get with the returned ids

Create. The response's created object is the only place the secret appears:

x:AppPassword/set
create: {
  "new": {
    "description": "read-only agent",
    "expiresAt": "2026-12-31T00:00:00Z",
    "allowedIps": {},
    "permissions": { "@type": "Inherit" }
  }
}

Revoke:

x:AppPassword/set
destroy: ["the-id"]

The methods require sysAppPasswordQuery, sysAppPasswordGet, sysAppPasswordCreate, sysAppPasswordUpdate, and sysAppPasswordDestroy. GET /api/account shows whether the signed-in person has them. A normal mailbox owner on the internal directory does.

Screens

  1. Sign in. Email and account password. Keep the session in the browser. Do not send it to any other host.
  2. List. Description, created date, expiry, IP limit, and permission mode. No secret column, because the server will not send it.
  3. Create. Description, optional expiry, optional IP list, and a permission choice that defaults to a mail-only set rather than Inherit. On success, show the secret once, with a copy button, and a warning that it cannot be shown again.
  4. Revoke. One confirmation. The row disappears. Existing connections using that password fail on their next login.

Do not add an edit box for the secret. The server rejects a caller-chosen password. Do not store the secret in the repo, in a log, or in local storage after the person leaves the page.

What not to mix in

  • Do not put this form on the webmail host. webmail.cryptocomputing.ca only forwards /jmap to Stalwart. The management call belongs on emailadmin.cryptocomputing.ca.
  • Do not let this page also read mail. Listing passwords is Door 2. Reading mail is Door 1. Two pages, two credentials.
  • The built-in Account Manager already does this job. Build a separate page only if you want a smaller screen, a mail-only permission preset, or a flow aimed at issuing one password for an agent.
